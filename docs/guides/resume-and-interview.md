## 一段项目介绍

**DevHarbor | 软件研发 AI 工作台**

面向软件研发场景，开发集问题分析、代码审查、CI 故障排查与项目知识问答于一体的 AI 工作台；结合多 Agent 编排与 RAG 检索，组织代码和文档证据，输出可追溯的分析建议，并通过人工确认执行外部操作。

当前实现接入 GitHub 仓库数据与本地代码工作区，操作草稿执行受支持的 GitHub 写入，并保留工具轨迹、评估记录与审计日志。产品介绍突出研发场景与工程能力，平台接入作为实现范围说明。

**技术栈：** Python、FastAPI、Pydantic、SQLAlchemy、PostgreSQL、Milvus、LangGraph、LangChain、Ragas；Next.js、React、TypeScript、Tailwind CSS。

其中 ChatAgent 实际使用 `StateGraph`、`StructuredTool` 与 `ChatOpenAI`；跨领域工作流由自定义异步编排器实现。数据库默认使用 PostgreSQL，隔离测试及轻量演示使用 SQLite；向量检索由 Milvus 承担。不要仅根据依赖清单把 pgvector、Redis 等写成已经落地的核心检索或任务队列组件。

## 简历条目模板

建议按岗位选取其中三条，再补上自己的职责范围和项目时间。以下描述没有预设个人贡献比例，也没有填入未经测量的提升数字。

- **Agent 编排：** 基于 LangGraph 构建模型决策与工具执行循环，接入代码检索、记忆检索及 Issue / PR / CI 专用 Agent；实现依赖就绪任务并发、单任务超时控制、失败依赖跳过与 Observer 驱动的有限重规划，形成可追溯的工程分析流程。
- **RAG 检索：** 实现按仓库隔离的 Milvus 向量与 BM25 关键词混合检索，结合加权融合、近重复去除、父文档片段限额、重排和同版本上下文扩展；通过证据门控与编号引用支持可核对的知识回答，并记录检索阶段和降级原因。
- **上下文与技能：** 实现基于 `SKILL.md` 的触发选择、指令及引用资源加载、工具约束与执行校验；结合上下文预算、微压缩和摘要边界管理长对话，保留工具调用配对与可回查的原始消息。
- **评估与操作确认：** 接入固定题集、硬规则和 RAGAS 指标，对真实 ChatAgent 路径采集回答、检索证据与工具轨迹；支持异常指标重评分和同基线回归比较，将待执行 GitHub 操作及评估问题转换为人工确认的 ActionDraft。

如果投递后端岗位，可以将“评估与操作确认”提前，重点讲清 API、持久化、失败处理与数据范围；投递 AI 应用岗位，则优先展开工具循环、检索流水线和评估方法。

## 90 秒讲解示例

> DevHarbor 是面向软件研发场景的 AI 工作台，解决问题记录、代码变更、CI 日志和项目知识分散的问题。例如判断一次代码变更是否具备合并条件，需要同时检查关联问题、变更内容、失败日志和项目约定。当前实现接入 GitHub 与本地代码工作区，让 Agent 检索证据、调用专用分析工具，并给出可追溯的建议。
>
> 技术上分两层：ChatAgent 用 LangGraph 管理模型决策和工具执行循环；遇到跨领域问题，再交给自定义工作流编排器。Planner 拆解任务，依赖满足的任务并发执行，Observer 检查证据缺口和冲突，必要时有限重规划，最后由 Synthesis 汇总。
>
> 知识检索采用向量和 BM25 混合召回，再做去重、重排、上下文扩展和回答门控。当前代码直接从工作区读取，对象状态回到同步快照或 GitHub 核查，必要时先刷新，避免让历史片段代替当前事实。
>
> 我会重点展示自己实际负责的模块、对应代码和失败场景测试。项目还提供工具轨迹、固定题集评估与人工确认草稿；目前定位是本地或受控单用户演示，尚未实现完整登录鉴权，也没有宣称生产规模下的效果收益。

最后一段请替换为自己的真实职责，例如“我主要负责检索流水线和评估链路”，再展示对应提交与测试。

## 建议演示顺序

1. **先讲一个真实问题。** 选一个自己熟悉的仓库、Issue 或 PR，说明所需证据分别在哪里。只展示可公开的数据。
2. **展示一次可回查的回答。** 打开工具轨迹和引用，说明哪个结论来自代码、哪个来自知识库、哪个需要进一步核查。轻量演示没有连接真实模型或向量服务时，明确指出当前降级模式。
3. **展开一个复杂流程。** 查看工作流的任务依赖、状态和 Observer 结果，解释任务失败或证据不足如何影响后续步骤。
4. **展示一个失败样例。** 可以使用现有回归测试说明重复工具调用、跨仓库数据、缺失证据或任务超时的处理。不要为了展示而对真实仓库执行修改。
5. **展示评估方法。** 说明固定题集、硬规则、语义评分以及指标异常的区别；如有真实评测结果，附上运行配置和原始记录，再谈结论。

## 当前边界与可继续推进的方向

| 当前边界 | 面试中合适的表述 | 后续可验证的工作 |
| --- | --- | --- |
| 单用户演示权限模型，未实现完整登录鉴权 | 实现了操作草稿确认和审计流程；当前授权模型仍需完善 | 接入真实身份、仓库级授权，并补充越权回归测试 |
| 工作流和评估后台任务在应用进程中运行 | 已有异步调度与任务状态；不声称跨进程恢复或分布式执行 | 验证重启恢复、幂等处理与持久化队列方案 |
| 确认外部写入后才保存执行结果 | 可以追踪成功/失败结果；不声称严格 exactly-once | 测试网络不确定结果和并发确认，设计防重复机制 |
| SQLite / deterministic embedding 是演示与测试路径 | 用于验证本地交互和确定性回归 | 单独完成 PostgreSQL、Milvus、真实 Embedding 与模型联调 |
| 内置题集覆盖范围有限 | 仓库提供项目说明资料的回归起点 | 增加真实任务、难负例、版本冲突和证据不足案例 |
| 混合检索与门控包含启发式策略 | 实现可解释的检索链路与拒答分支 | 在固定基线上分别比较纯关键词、纯向量、混检及重排效果 |

没有实际测量时，不写“效率提升 80%”“准确率 95%”“支持百万文档”“高并发生产落地”或“完全自主研发协作”。内置测试通过与真实模型质量、数据库规模性能是不同证据。

## 如何补上可信的量化结果

保留同一份数据与问题集，记录代码提交、题集 Hash、模型/Embedding/Judge 配置、检索方式、Top-K 和运行环境，再比较一个明确变量。至少保存：

- 检索的命中情况、Precision@K / Recall@K 等实际运行输出，以及样本量。
- 硬规则通过情况与 RAGAS 指标；分别记录缺失评分、运行失败和质量未达标。
- 回答或任务耗时分布、失败率、模型使用量；估算 Token 与提供商返回用量分开。
- 失败案例和适用范围，避免只挑选成功问题。

确认实验可复现后，才把数字填入简历，例如：“在固定的 **N 条自建问题**、**指定模型与检索配置** 下，相比 **明确基线**，**指定指标** 从 A 变为 B。”若没有这些记录，使用上面的实现型描述即可。
